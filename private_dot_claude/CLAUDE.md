# CLAUDE.md

## 基本ポリシー

1. 回答は必ず日本語で行う。
2. セッション開始時、作業に入る前に現在のブランチ名と Git ステータスを確認し、これから行う作業に対してブランチが適切かを確かめる。並行セッションと競合しうる場合は worktree を検討する。
3. 非自明な変更（複数ファイル・新規設計・アーキテクチャへの影響・不可逆な操作）は、着手前に目的・前提・全体設計・ブランチ戦略・コミット設計を固める。設計する場合は `Plan` モードに切り替える。自明・単一箇所・可逆な変更は、情報が揃っていればそのまま着手してよい。
4. 曖昧さと未知の扱い:
   * ユーザーにしか決められないこと（好み・業務ルール・スコープ・不可逆な結果に関わる判断）は着手前に確認する。選択肢から選んでもらう質問は `AskUserQuestion` を使い、選択肢を地の文の箇条書きで並べない。
   * 一般的に標準解がある判断は、採用した前提を明示した上でそのまま進めてよい。
   * 暗黙の前提・盲点・違和感・矛盾に気づいたら、その場で報告する。
   * 推測で埋めない。推測が必要な場合は推測であると明記する。分析・提案の作法は `~/.claude/rules/fact-based-evaluation.md` を参照。
5. 知識は古い可能性がある。外部サービス・ライブラリの挙動が結果を左右する箇所や確信が持てない箇所は、着手前に Context7 または公式ドキュメントで最新仕様を確認する。
6. 記録: 要件・検討・調査結果（サブエージェントに委任した調査の結果も含む）を notes worktree の `context/<NNN>_<context-name>/` 配下（`requirements/` / `deliberation/` / `research/`、ファイル名は `<対象名>_YYYY-MM-DD.md`）に残す。一度保存した調査記録は過去の記録として価値があるため、メンテナンス不要。

## 自律実行とサブエージェント

* **独立したサブタスクは委任する。** 独立に進められる調査・実装・検証は積極的にサブエージェントへ委任し、走っている間も自分の作業を続ける。サブエージェントが脱線した・文脈が欠落していると分かったときだけ介入する。
* **長時間タスクは独立サブエージェントで検証する。** 自己批評より、新規コンテキストを持つ独立した検証サブエージェントの方が精度が高い。長く走るタスクでは一定間隔で仕様と突き合わせて検証する。

## 設計・実装ポリシー

* **判断の優先順位**: ① プロジェクト固有の明文ルール（CLAUDE.md・コーディング規約・ADR） ② 既存コードベースのパターン ③ 一般的なベストプラクティス。
* **コロケーション**: 機能に必要なファイル（コンポーネント・スタイル・テスト・型定義・ユーティリティ）は同じディレクトリにまとめる。特定機能でしか使わないものをグローバルな共通ディレクトリに置かない。
* **共通化**: 実装前に流用できる既存資産を確認する。3 箇所以上で使う見込みがあれば共通化を検討し、1 箇所だけなら共通化しない（YAGNI）。共通化・リファクタリングは機能実装とコミット / ブランチを分ける。

## コード変更後の検証

コミット前に、変更に関連するテスト・型チェック・リントを実行し、新規エラーがないことを確認する。具体的なコマンドはプロジェクトごとの CLAUDE.md の `Development Commands` セクションに従う。
