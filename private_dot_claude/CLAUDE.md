# CLAUDE.md

## 基本ポリシー

1. 回答は必ず日本語で行う。
2. セッション開始時、作業に入る前に以下を確認する。
   * 現在のブランチ名と Git ステータス（未コミット変更の有無）
   * これから行う作業に対して現在のブランチが適切かをユーザーに確認する
   * 並行して別セッションから指示が出される可能性を考慮し、worktree の使用を検討する
3. **非自明な変更**（複数ファイル・新規設計・アーキテクチャに影響する変更・不可逆な操作を伴うもの）に入る前に、下記を明確化・設計する。設計する場合は `Plan` モードに切り替える。自明・単一箇所・可逆な変更は、情報が揃っていれば設計フェーズを省いて着手してよい。
   * 目的・背景・前提条件
   * 全体設計
   * ブランチ戦略・ブランチ設計
   * コミット設計
4. 判断が曖昧なとき、それが着手を妨げる／不可逆な結果に関わる／ユーザーにしか答えられない場合は、クリアにしてから着手する。それ以外の可逆な一歩は、合理的な既定を選んで進めてよい（その際、何を仮定したかは明記する）。
  * 選択肢を提示して選んでもらう質問は `AskUserQuestion` ツールを使う
    （例: ブランチ戦略をA/B/Cから選ぶ、プリセット名の候補から選ぶ等）
  * 自由記述で答えてほしい質問や単純な確認は、応答本文で聞いてよい
  * 選択肢化できる質問を地の文の箇条書きで並べない
    （箇条書きで選ばせたくなった時点で `AskUserQuestion` を使うサイン）
5. 違和感・矛盾を見つけた場合は必ず報告する。
6. 分からないことを推測で埋めない
  * 推測しなければ思考できない場合は、何が推測であるかを明言・明記すること。
  * ユーザーの発言から勝手に結論・決定・方針を拡張しない（比較・評価で片方に加担しない）。
  * 詳細・作法・失敗パターンは `~/.claude/rules/fact-based-evaluation.md` を参照。
7. 知識は古い可能性があるため、外部サービス・ライブラリの**挙動が結果を左右する箇所**や**確信が持てない箇所**では、着手前に最新仕様を確認する（既知で確信のある範囲まで都度調査する必要はない）。
   1. Context7または公式ドキュメントに直接アクセスし、最新仕様を確認
   2. 調査結果は実装根拠として `.notes/context/<NNN>_<context-name>/research/<対象名>_YYYY-MM-DD.md` に保存
      * 一度保存した記録は過去の記録として価値があるため、メンテナンス不要
8. 対話中の要望や要件に関わる情報を常に `.notes/context/<NNN>_<context-name>/requirements/requirements_YYYY-MM-DD.md` に記録する。
9. 検討したことは再度検討しなくていいよう `.notes/context/<NNN>_<context-name>/deliberation/deliberation_YYYY-MM-DD.md` にメモする。

## 自律実行とサブエージェント

* **独立したサブタスクは委任する。** 独立に進められる調査・実装・検証は積極的にサブエージェントへ委任し、走っている間も自分の作業を続ける。サブエージェントが脱線した・文脈が欠落していると分かったときだけ介入する。
* **長時間タスクは独立サブエージェントで検証する。** 自己批評より、新規コンテキストを持つ独立した検証サブエージェントの方が精度が高い。長く走るタスクでは一定間隔で仕様と突き合わせて検証する。

## 設計・実装ポリシー

### 優先順位

設計・実装の判断は以下の順で従う：

1. **プロジェクト固有のルール** - CLAUDE.md、コーディング規約、ADR など明文化されたもの
2. **既存コードベースのパターン** - 類似実装が既にあればそれに従う
3. **一般的なベストプラクティス** - 上記がない場合に適用

### コロケーション（Colocation）

関連するコードは近くに配置し、理解しやすく保守しやすい構造を維持する。

* 機能に必要なファイル（コンポーネント、スタイル、テスト、型定義、ユーティリティ）は同じディレクトリにまとめる
* 特定の機能でしか使わないものをグローバルな共通ディレクトリに置かない
* ディレクトリ構造を見ただけで、その機能の全体像が把握できる状態を目指す

### 共通化と再利用

実装前に既存資産（コンポーネント・ユーティリティ・型定義・類似実装パターン）を確認し、流用できるものは計画に盛り込む。共通化のメリット（保守性・一貫性）とデメリット（過度な抽象化）を天秤にかける。

* **判断基準**: 3箇所以上で使う見込みがあれば共通化を検討。1箇所でしか使わないものを「将来のため」に共通化しない（YAGNI）。
* **既存パターン優先**: 類似実装があればそのパターンに従う。無ければ一般原則＋周辺コードのスタイル（ディレクトリ構成・共通部品の整備状況）に合わせる。
* **別工程で行う**: 共通化・リファクタリングは機能実装と混ぜず、コミット / ブランチを分けて意図を明確にする。

## コード変更後の検証

コードを変更した後、コミット前に以下を実行して新規エラーがないことを確認する：

1. **テスト** - 変更に関連するパッケージ/サービスのテストを実行
2. **型チェック（typecheck）** - mypy 等で型整合性を確認
3. **リント（lint）** - ruff 等でコード品質を確認

具体的なコマンドはプロジェクトごとの CLAUDE.md の `Development Commands` セクションに従う。
