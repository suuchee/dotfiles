# Git revert 粒度

Git の作業を残すときは、**「あとで戻したい単位」で粒度を設計する** ことを原則とする。

## なぜ

粒度設計の目的は **そのブランチでの作業を戻しやすくすること**。戻しやすさは自分のためでもあり、他の作業者のためでもある。

- 自分しかそのブランチで作業しないなら、自分があとで戻したいとき・別の作業に切り替えたいときに困らない粒度にしておく
- 複数人で作業するなら、レビュー・revert・cherry-pick がしやすい粒度にしておく（複数人ならほぼ必須意識）
- 「自分用か複数人用か」をその都度判断するのは無理なので、**常に戻せる粒度を意識する**

## 原則: 1 ブランチ = 1 単位

ブランチは 1 つの単位（リファクタリング / 機能追加 / 修正 等）に対応させる。この前提が成立すれば、ブランチ / PR 単位の revert で整合性が保てる。

ブランチ内のコミット粒度はレビューや履歴の見通しに合わせて自由に分割してよい（ブランチ単位で戻せるため、コミット間で一時的に整合性が壊れていても許容される）。

ブランチを 1 単位に保つ判断・操作は `~/.claude/skills/git/references/branch-strategy-pivot.md` を参照。

## 例外: 1 ブランチに複数単位が混ざる場合

やむを得ず 1 ブランチに複数の単位が混ざる場合は、**コミット単位の revert で整合性が保てるよう、各単位を 1 コミットにまとめる**。粒度は「片方だけ revert したときに整合性が壊れるかどうか」で判断する。

### 1 コミットにまとめるべき操作（例）

| 操作 | 同一コミットに含めるもの | 別コミットにすると起きること |
| --- | --- | --- |
| 切り出し（extract） | 切り出し先の新規作成 / 切り出し元からの該当箇所削除 / 切り出し元から先への参照追加 | 片方だけ revert すると参照先が無い・同じ内容が 2 箇所に残る |
| ファイル名変更・移動 | `git mv` / 参照側の import・リンク更新 | import / リンクが壊れる |
| API・関数のリネーム | 定義 / 全呼び出し側 | ビルド・テストが壊れる |
| 設定キー・スキーマ変更 | 設定ファイル / それを読むコード | 読み出しが壊れる |

ファイル数が多い・新規追加と既存改修で type が違う（`feat` と `refactor` 等）を理由に分けない。**1 つの操作で生じる差分は 1 コミット**。
