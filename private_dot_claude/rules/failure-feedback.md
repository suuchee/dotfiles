# 失敗の還流

発見した失敗を、ガイド文ではなく仕組み（rule / test / hook / skill）に戻す。同じ失敗を繰り返さないことが目的。

## 原則

1. **同じ失敗を 2 度繰り返したら仕組みに戻す。** テキスト追加は advisory に過ぎない。2 度目を観測したら deterministic な仕組み（test / lint / hook、または手順を強制する skill）への昇格を検討する。
2. **パターン単位で抽象化する。** 具体の修正だけで終わらせず、「このクラスの誤りを次回どう防ぐか」を 1 行で言語化する。
3. **足す前に既存の仕組みを点検する。** 文言が曖昧なら書き直す、読まれない場所なら移す、例示不足なら例を足す。新規追加は仕組みが無い場合のみ。同じ目的の仕組みを 2 つ作らない。3 度以上再発するなら設計自体を疑う。
4. **具体と抽象を二層で残す。** 具体（再現できる eval / test）は 1 度目から残してよい。抽象（skill / rule への昇格）は 2 度目から。層を混ぜない（skill 本文に生の失敗事例を貼らない、eval に抽象論を書かない）。

## 戻し先

| 戻し先 | 適する場合 |
| --- | --- |
| `rules/` への追記・修正 | 全プロジェクト・全セッションで常時効かせたい判断基準・規範。常時コンテキストに載るため、状況依存の手順・詳細な事例列挙は置かない |
| test / lint | 機械的に検証できるもの |
| hook | 必ず毎回発火させたい操作（`settings.json` に書く） |
| skill | 手順化できる繰り返し作業。発火時にだけ読めば十分な詳細な手順・事例はこちら |

eval の置き場所・フォーマット・昇格の判断手順は `archive-to-canonical` skill を参照。
