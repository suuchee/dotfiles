# 失敗の還流

発見した失敗を、ガイド文ではなく仕組み（rule / test / hook / skill）に戻す。同じ失敗を繰り返さないことが目的。

## 1. 同じ失敗を 2 度繰り返したらガイドではなく仕組みに戻す

`CLAUDE.md` / `rules/` / skill のテキスト追加は advisory に過ぎず、確実な再発防止にはならない。
2 度目を観測したら、deterministic な仕組み（test / lint / hook、または手順を強制する skill）への昇格を検討する。

## 2. その場限りのパッチで終わらせない

具体の修正だけで満足せず、「このクラスの誤りを次回以降どう防ぐか」を 1 行で言語化する。
ファイル単位 / コミット単位ではなく、**パターン単位**で抽象化する。

## 3. 仕組みを足す前に既存の仕組みを点検する

新しい rule / test / hook を追加する前に、**既存の仕組みでなぜ防げなかったのか**を確認する。

| 既存仕組みが効かなかった理由 | 取るべき対処 |
| --- | --- |
| 文言が曖昧 | 既存 rule を書き直す（追加しない） |
| 配置が遅すぎ・読まれない場所 | 既存 rule の位置を変える / 上位 doc から参照する |
| 例示が不足 | 既存 skill / rule に例を足す |
| そもそも仕組みが無い | 新規追加 |

「同じ目的の仕組みが 2 つある」状態を作らない。3 度以上同じパターンが再発するなら、パッチを足し続けるのではなく、設計自体を疑う。

## 4. 戻し先の判断

| 戻し先 | 適する場合 |
| --- | --- |
| `rules/` への追記・修正 | 思想・判断基準として残せる規範 |
| test / lint | 機械的に検証できるもの |
| hook | 必ず毎回発火させたい操作（人間が事前設計して `settings.json` に書く） |
| skill | 手順化できる繰り返し作業 |

判断と昇格の手順は `archive-to-canonical` skill を参照。
