# 失敗の還流

発見した失敗を、ガイド文ではなく仕組み（rule / test / hook / skill）に戻す。同じ失敗を繰り返さないことが目的。

## 1. 同じ失敗を 2 度繰り返したらガイドではなく仕組みに戻す

`CLAUDE.md` / `rules/` / skill のテキスト追加は advisory に過ぎず、確実な再発防止にはならない。
2 度目を観測したら、deterministic な仕組み（test / lint / hook、または手順を強制する skill）への昇格を検討する。

## 2. その場限りのパッチで終わらせない

具体の修正だけで満足せず、「このクラスの誤りを次回以降どう防ぐか」を 1 行で言語化する。
ファイル単位 / コミット単位ではなく、**パターン単位**で抽象化する。

## 3. 仕組みを足す前に既存の仕組みを点検する

新しい rule / test / hook を追加する前に、**既存の仕組みでなぜ防げなかったのか**を確認する。

| 既存仕組みが効かなかった理由 | 取るべき対処 |
| --- | --- |
| 文言が曖昧 | 既存 rule を書き直す（追加しない） |
| 配置が遅すぎ・読まれない場所 | 既存 rule の位置を変える / 上位 doc から参照する |
| 例示が不足 | 既存 skill / rule に例を足す |
| そもそも仕組みが無い | 新規追加 |

「同じ目的の仕組みが 2 つある」状態を作らない。3 度以上同じパターンが再発するなら、パッチを足し続けるのではなく、設計自体を疑う。

## 4. 戻し先の判断

| 戻し先 | 適する場合 |
| --- | --- |
| `rules/` への追記・修正 | 思想・判断基準として残せる規範 |
| test / lint | 機械的に検証できるもの |
| hook | 必ず毎回発火させたい操作（人間が事前設計して `settings.json` に書く） |
| skill | 手順化できる繰り返し作業 |

判断と昇格の手順は `archive-to-canonical` skill を参照。

## 5. 具体と抽象を二層で残す

失敗を仕組みに還流するとき、**具体の出来事と抽象化したルール** は別の場所に分けて残す。両者は役割が違うので統合しない。

| 層 | 何を残すか | トリガー |
| --- | --- | --- |
| 具体（eval / test） | 起きた状況を再現できる prompt・入力・期待挙動・アンチパターン | **1 度目から残してよい**（2 度目を待たない） |
| 抽象（skill / rule） | 個別ケースから引き抜いた判断基準・チェックリスト・原則 | # 1 と同じ（同じ失敗を 2 度繰り返したら昇格） |

### なぜ二層に分けるか

- **eval は回帰防止に効く**: skill 改修時に同じ prompt を回せば、過去ケースの再発を機械的に検知できる。「スキルがある状態と無い状態で差が出るか」の A/B 検証にも使える
- **skill / rule 本文は判断基準として効く**: 抽象化されたルールは未知のケースに適用できる。具体例の羅列は本文を肥大化させ、判断軸を埋没させる
- **層が混ざると両方の効果が落ちる**: skill 本文に生の失敗事例を貼ると本文がノイズで埋もれ、eval に抽象論を書くと grader で検証できない

### 具体（eval）の置き場所

| ケース性質 | 置き場所 | 形式 |
| --- | --- | --- |
| 該当スキルが既に存在する | `~/.claude/skills/<skill>/evals/manual-cases.json` | skill-creator スキーマ準拠 JSON。アンチパターンは `expectations[]` に「〜が含まれていない」命題として記述 |
| 該当スキルが存在しない | `~/.local/share/chezmoi/.notes/pdca-cases/inbox/<area>/YYYY-MM-DD_<slug>.md` | 1 ケース 1 ファイル Markdown。フォーマットは pdca-cases リポジトリの README 参照 |

スキルあり側のケースは `~/.local/share/chezmoi/.notes/pdca-cases/INDEX.md` にパスを 1 行追記する（シンボリックリンクは作らない。両者とも chezmoi 経由で git 管理されるため二重化不要）。

#### なぜ「該当スキルなし」を memory ではなく外部リポジトリに置くか

- claude code の memory はコンテキストに毎回ロードされる → 蓄積するとコンテキスト圧迫
- skill 内 eval は呼出時のみロード → 局所化される
- 「該当スキルなし」を `~/.claude/` 直下に置くと Claude Code の予約名・更新と衝突するリスクあり → ユーザー領域明示済みの `skills/` / `rules/` 配下以外には新規ディレクトリを作らない
- chezmoi リポジトリの `.notes/`（`dot_` プレフィックス無し）はホームへの展開対象外で、git 管理だけ残る個人領域として使える

### eval ファイル名の注意

skill-creator は `evals/evals.json` を正式スキーマとして自動生成・更新する可能性がある。
人手で蓄積する eval は **`evals/manual-cases.json` のような別ファイル名**にして衝突を避ける。

### 運用上の注意

- 1 度目の失敗で eval を残すだけで止めてよい。抽象化（skill 本文への追記）は 2 度目以降または抽象化のパターンが見えた時点で行う
- inbox 配下のケースは半年以上 promoted（skill 化）も dropped（捨てる）もされないものは振り返って削除候補（lossy 運用、`pdca-cases/README.md` 参照）
