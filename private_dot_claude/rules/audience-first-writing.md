# audience-first writing

人に読まれるテキストは、**読者・読む場面・読後の行動を決めてから書く**。

## 原則

**読者の理解・判断・行動に必要な情報だけを、読者が使える形で本文に置く。**

書く前、または書いた直後に確認する。

> この文を削ったら、読者の理解・判断・行動は変わるか？

変わらないなら、削るか、適切な場所へ移す。

## 書く前に決めること

- 誰が読むか
- いつ読むか
- 読んだ後に何を理解・判断・実行できるべきか
- その情報は本文に置くべきか、別の場所に置くべきか

## 本文に入れないもの

読者の目的に直接つながらない限り、以下は本文に入れない。

- 作業方針や使ったルールの説明
- 採用しなかった案への弁明
- 書き手の不安、予防線、言い訳
- 内部用語、内部の時間軸、内部の分類名
- 書き手自身に向けた補足

必要なら、README、PR description、ADR、CHANGELOG、notes、コメント、Runbook など、読む人と読む場面に合う場所へ移す。

## 例外

読者がレビューア、判断者、将来の保守者である場合、背景・代替案・制約・トレードオフは重要な本文情報になる。

ただし、その場合も作業ログをそのまま書かず、判断に必要な形へ要約する。

## 代表的な置き場所

- **README**: 初めて使う人向け。目的、始め方、前提、よく使う手順を書く。
- **PR description**: レビューア向け。変更内容、理由、影響範囲、見てほしい点を書く。
- **コミットメッセージ**: 履歴を読む人向け。変更単位、理由、影響を書く。作業手順は書かない。
- **ADR / 設計ドキュメント**: 判断を追う人向け。決定、理由、代替案、トレードオフを書く。
- **CHANGELOG / リリースノート**: 利用者・運用者向け。変更点、影響、移行要否を書く。
- **Runbook / トラブルシュート**: 障害対応者向け。症状、確認手順、復旧手順を書く。
- **CLI help / API reference**: 作業中に仕様を確認する人向け。構文、引数、戻り値、制約を書く。
- **自分用メモ**: 自分向け。未整理の考え、調査ログ、仮説、没案を書く。

## 出力前チェック

- 主読者は明確か
- 読む場面は明確か
- 読者がその場で使える形になっているか
- 経緯、迷い、没案、作業方針が本文に混ざっていないか
