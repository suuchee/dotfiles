# audience-first writing

人に読まれる名前・タイトル・本文・コメントは、
読者がその場で知りたい問いに答えるために書く。

## 原則

書く内容を、情報の種類で先に決めない。

作業手順・背景・経緯・理由・制約・影響・注意点は、どれも必要になる場合がある。
重要なのは、それが読者の問いに答えているかどうかである。

書く前に、次を決める。

* 誰が読むか
* いつ、何のために読むか
* 読者はその場で何を知りたいか
* 読者は読後に何を判断・実行するか

複数読者がいるなら主読者を明示し、副読者には別経路（リンク・別ファイル）を用意する。
時間で読者が変わるなら、最も長く読む読者を想定する（コメントなら数ヶ月〜数年後の改修者）。

## 作業者視点ではなく対象視点で書く

audience-first ではない失敗の多くは「作業者の手元の動き」が混入することで起きる。

書き手や AI は、作業中に多くの情報を知っている。
どこから持ってきたか、どの順番で作業したか、途中で何を試したか、
以前どこに置いていたか、AI に何を指摘されたか、なぜ迷ったか、作業中に何を発見したか。
これらは書き手にとって自然な情報だが、読者が知りたいこととは限らない。

「何をしたか」「なぜ」「何のために」のいずれも、
作業者の経路ではなく対象側の意味で表す。

例（変更内容）：

| 作業者視点 | 対象視点 |
| --- | --- |
| アーカイブから復元した | 不足していた参照ドキュメントを追加した |
| 旧ファイルから移動した | 関連情報の参照先を統一した |
| AI に指摘されたので修正した | 矛盾していた記述を修正した |
| 一度消したものを戻した | 必要な判断基準を再追加した |

例（名前・タイトル）：

| 作業者視点 | 対象視点 |
| --- | --- |
| `restore-from-archive` | `expand-git-skill-references` |
| `move-old-docs` | `add-merge-strategy-guidance` |
| `retry-fix` | `unify-alert-setting-docs` |
| `temporary-update` | `clarify-worktree-rename-steps` |
| `getUserFromMysql` | `findUser` |
| `tmp`, `data`, `processData` | `pendingInvoices`, `normalizeAddress` |

作業者視点の情報そのものが読者の問いに答える場合
（自分用メモ、Runbook 中の手順、デバッグ記録、設計判断の経緯など）は書いてよい。
そうでない場合は、対象に起きた変化を書く。

## 「なぜ」の書き方

読者が知りたい「なぜ」は、作業者がそうした事情ではなく、対象側の必要性である。
次のどれかとして書く。

* 不足していたもの
* 解決したい問題
* 守るべき制約
* 防ぎたい失敗
* 明確にしたい判断
* 読者への影響

| 悪い例 | 良い例 |
| --- | --- |
| アーカイブに残っていたため復元した | マージ戦略の判断基準が不足していたため追加した |
| 以前のファイルにあったため移動した | 関連情報が分散していたため参照先を統一した |
| 念のため追加した | 同じ判断ミスを防ぐため確認条件を明記した |

## 出力前チェック

出力前に確認する。

* 読者は誰か、いつ何のために読むか
* この文・名前は、読者がその場で知りたい問いに答えているか
* 作業者の手元の動きではなく、対象に起きた変化を書いているか
* 理由を書く場合、作業者の都合ではなく対象側の必要性を書いているか
* 名前やタイトルが、作業経路ではなく対象の意味を表しているか
