# audience-first writing

人に読まれるテキストは、**読者と読むタイミングを決めてから書く**。

## 最重要原則

**書き手の事情を、読者の目的に接続せずに本文へ持ち込まない。**

書く前、または書いた直後にこれだけ確認する。

> この文を削ったら、読者の理解・判断・行動は変わるか？

変わるなら残す。変わらないなら、削るか、適切な場所へ移す。

ここでいう本文とは、その文書の主読者が目的達成のために読む中心部分を指す。

## なぜ守るのか

書き手は、作業の経緯、設計上の迷い、却下した案、使ったルール、将来の予定を知っている。しかし読者が知りたいのは、多くの場合それではない。

読者は、自分の状況で必要なことを理解し、判断し、実行するために読む。文章はその目的に役立つ形へ情報を変換してから置く。

## 基本

- **誰が読むかを決める**
  - 利用者、レビューア、運用者、コントリビューター、障害対応者、将来の自分など、読者を具体化する。
- **いつ読むかを決める**
  - 初見、作業中、レビュー中、障害対応中、履歴調査中など、読む状況を具体化する。
- **読者に必要な形で書く**
  - 読者が見る名前、使うコマンド、判断に必要な差分、復旧に必要な手順など、その場で使える形にする。
- **書く場所を分ける**
  - 使い方は README、構文は help / API doc、変更履歴は CHANGELOG、判断の背景は ADR、検討経緯は notes、変更の意図はコミットメッセージや PR description に置く。

## 書く前チェック

- 誰が読むか
- いつ読むか
- 読んだ後に何を理解・判断・実行できるべきか
- その情報はどこに置くべきか

## 本文から外すもの

- 使ったルールや作業方針の説明
- 採用しなかった案への弁明
- 書き手の不安、予防線、言い訳
- 内部用語、内部の時間軸、内部の分類名
- 本文の読者ではなく、書き手自身に向けた補足

必要なら、本文ではなく適切な場所へ移す。

## 例外

読者が判断者、レビューア、将来の保守者である場合、背景・代替案・制約・トレードオフは本文の中心情報になる。

その場合も、作業ログをそのまま書くのではなく、読者の判断に必要な形へ要約する。

## 代表的な置き場所

以下は参考例であり、厳格な分類ではない。迷ったら表に合わせるのではなく、実際に読む人と読む場面を優先する。

| 書く場所 | 主な読者 | 読む場面 | 書くこと |
| --- | --- | --- | --- |
| README | 初めて使う人、評価する人、あとで使い直す人 | 導入前、セットアップ時、使い方を忘れた時 | 何ができるか、どう始めるか、必要な前提、よく使う手順 |
| PR description | レビューア、将来の保守者 | レビュー時、変更理由をあとで追う時 | 何を変えたか、なぜ必要か、影響範囲、確認してほしい点 |
| コミットメッセージ | 履歴を読む人、bisect する人、将来の自分 | 変更の意図を履歴から調べる時 | 変更の単位、理由、影響。使ったルールや作業手順は書かない |
| コード中のコメント | そのコードを読む実装者、レビューア、将来の自分 | 実装意図や例外的な判断を確認する時 | コードだけでは分からない理由、制約、注意点。処理内容の言い換えは書かない |
| Issue | 作業する人、優先度を決める人、状況を追う人 | 着手前、トリアージ時、進捗確認時 | 問題、期待する状態、再現手順、完了条件、制約 |
| AI 向けプロンプト / agent 指示 | AI agent、それを保守する人 | 実行時、失敗時、指示を更新する時 | 目的、入力、制約、成功条件、禁止事項、出力形式。書き手の経緯ではなく、実行に必要な条件を書く |
| CHANGELOG / リリースノート | 利用者、運用者、アップグレード担当者 | 更新前、更新後、影響確認時 | 何が変わったか、影響、移行が必要か、注意点 |
| エラーメッセージ | 失敗に遭遇した人 | エラー発生時、復旧時 | 何が起きたか、原因の手がかり、次に試すこと |
| トラブルシュート / Runbook | 障害対応者、運用者、将来の自分 | 障害対応中、復旧後の確認時 | 症状、確認手順、復旧手順、エスカレーション条件 |
| ADR / RFC / 設計ドキュメント | 将来の実装者、レビューア、チームメンバー | 判断の背景を確認する時、設計を変更する時 | 決定、理由、代替案、トレードオフ |
| CLI help / API reference | 作業中に仕様を確認する人 | 引数、戻り値、制約を確認する時 | 構文、引数、戻り値、制約、短い例 |
| レビューコメント | 変更を書いた人、あとで議論を読む人 | 修正中、議論の経緯を追う時 | 問題、理由、期待する修正。好みだけなら書かない |
| テスト名 / テストコメント | 失敗したテストを見る人、仕様を読む人 | テスト失敗時、仕様確認時 | どの振る舞いを保証しているか、なぜそのケースが重要か |
| 設定ファイル内コメント | 設定を変更する人、運用者 | 値を変更する時、設定の意味を確認する時 | 値の意味、変更してよい範囲、注意点 |
| 自分用メモ | 自分、近い将来の自分 | 考えを整理する時、あとで再開する時 | 未整理の考え、調査ログ、比較、仮説、没案 |
| チーム向けドキュメント | チームメンバー、オンボーディング中の人 | 運用、引き継ぎ、判断の確認時 | 共通手順、判断基準、責任範囲、変更時の注意 |
| 外部向けドキュメント | ユーザー、導入検討者、外部開発者 | 利用、評価、連携、問い合わせ前 | 公開された仕様、使い方、制約、サポートされる範囲 |

## 出力前チェック

- 主読者は明確か
- 読む場面は明確か
- 読者の理解・判断・行動に不要な説明が混ざっていないか
- 経緯、迷い、没案、作業方針を適切な場所へ分離したか
- 読者がその場で使える名前、コマンド、手順、判断材料になっているか
