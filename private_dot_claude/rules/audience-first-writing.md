# audience-first writing

人に読まれるテキストは、**読者・読む場面・読後の行動を決めてから書く**。

## 原則

**読者の理解・判断・行動に必要な情報だけを、読者が使える形で本文に置く。**

書く前、または書いた直後に確認する。

> この文を削ったら、読者の理解・判断・行動は変わるか？

変わらないなら、削るか、適切な場所へ移す。

## 書く前に決めること

- 誰が読むか
- いつ読むか
- 読んだ後に何を理解・判断・実行できるべきか
- その情報は本文に置くべきか、別の場所に置くべきか
- 経緯（背景・履歴）を本文に含めるか

## 本文に入れないもの

読者の目的に直接つながらない限り、以下は本文に入れない。

- 作業方針や使ったルールの説明
- 採用しなかった案への弁明
- 書き手の不安、予防線、言い訳
- 内部用語、内部の時間軸、内部の分類名
- 書き手自身に向けた補足

必要なら、README、PR description、ADR、CHANGELOG、notes、コメント、Runbook など、読む人と読む場面に合う場所へ移す。

## 例外

読者がレビューア、判断者、将来の保守者である場合、背景・代替案・制約・トレードオフは重要な本文情報になる。

ただし、その場合も作業ログをそのまま書かず、判断に必要な形へ要約する。

## 経緯（背景・履歴）を入れるか

「アーカイブから復元した」「以前はこういう経緯で変えた」「もともと別ファイルだった」のような書き手側の文脈は、**読者ごとに切り分ける**。名前付け（ブランチ名・ファイル名・関数名）やドキュメントを書くときは、書く前に問う：

> この経緯を読み手は知る必要があるか？ 知らないと判断・行動を誤るか？

- **Yes** → 入れる（作業ログのまま貼らず、要約して判断に使える形で）
- **No** → 入れない。経緯は別の場所（自分用メモ、ADR、PR description 等）へ

### 入れる場面

- ADR / 設計ドキュメント — 決定の根拠としての経緯・代替案・トレードオフ
- PR description — レビュアーが変更理由を理解するための背景
- 保守者向けコメント — なぜこの実装になったかを将来の読者に伝える

### 入れない場面（特に注意）

- **コミットメッセージ・ブランチ名** — 外部目線では「実際の変更内容」が主。「アーカイブから復元」より「マージ戦略の選択指針を追加」のように、変更内容で表現する
- **公開 README / docs / CLI help** — 利用者は内部事情を知らないし関心もない
- **ファイル名・関数名・スキーマ名等の命名** — 「旧名」「リネーム経緯」は名前そのものに残さない

特に **書き手にしか意味のない経緯**（「リストアした」「前は別名だった」「最初は失敗した」等）に注意。読者には「実際の変更内容」「実際の現状」だけが見えるので、経緯はノイズになる。

## 代表的な置き場所

- **README**: 初めて使う人向け。目的、始め方、前提、よく使う手順を書く。
- **PR description**: レビューア向け。変更内容、理由、影響範囲、見てほしい点を書く。
- **コミットメッセージ**: 履歴を読む人向け。変更単位、理由、影響を書く。作業手順は書かない。
- **ADR / 設計ドキュメント**: 判断を追う人向け。決定、理由、代替案、トレードオフを書く。
- **CHANGELOG / リリースノート**: 利用者・運用者向け。変更点、影響、移行要否を書く。
- **Runbook / トラブルシュート**: 障害対応者向け。症状、確認手順、復旧手順を書く。
- **CLI help / API reference**: 作業中に仕様を確認する人向け。構文、引数、戻り値、制約を書く。
- **自分用メモ**: 自分向け。未整理の考え、調査ログ、仮説、没案を書く。

## 出力前チェック

- 主読者は明確か
- 読む場面は明確か
- 読者がその場で使える形になっているか
- 経緯、迷い、没案、作業方針が本文に混ざっていないか
