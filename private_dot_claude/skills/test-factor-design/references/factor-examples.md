# テスト種別ごとの典型要因例

各テストカテゴリで「どんな要因を考えると効くか」のチートシート。要因を列挙する Step 1 の出発点として使う。

## 1. unit test の境界値テスト

| 要因 | 典型的な水準 |
| --- | --- |
| 入力の型 | string / number / boolean / array / null / undefined |
| 値の範囲 | 最小 / 典型 / 最大 / 範囲外 / 0 / 負数 / 空 |
| 状態 | 初期状態 / 中間状態 / 完了状態 / エラー状態 |
| 並行性 | 単一呼び出し / 多重呼び出し / 順序依存 |
| 副作用の有無 | 純粋関数 / I/O あり |
| エラー条件 | 正常 / 想定内エラー / 想定外エラー |

## 2. integration test

| 要因 | 典型的な水準 |
| --- | --- |
| 認証状態 | 未認証 / 認証済み / 期限切れトークン / 権限不足 |
| データ状態 | 空 / 1 件 / 多数 / 巨大 / 不整合 |
| 外部依存の応答 | 200 / 4xx / 5xx / タイムアウト / 切断 |
| 並行性 | 単一 / 並行 / 競合 |
| トランザクション境界 | 単一トランザクション / 複数 / ネスト |
| キャッシュ状態 | 未キャッシュ / 有効 / 期限切れ / 無効化済み |

## 3. e2e / シナリオテスト

| 要因 | 典型的な水準 |
| --- | --- |
| ユーザー種別 | 未ログイン / 一般 / 管理者 / ゲスト |
| 入力経路 | UI / API 直接 / モバイル / バッチ |
| ブラウザ | Chrome / Safari / Firefox / モバイル |
| データ前提 | 空 / 既存データあり / マイグレーション済み |
| 例外状況 | 通常 / 通信エラー / タイムアウト / 権限変更中 |

## 4. LLM の trigger eval

| 要因 | 典型的な水準 |
| --- | --- |
| ドメイン | 主対象 / 隣接（trigger 不要） / 完全に無関係 |
| 言語 | 日本語のみ / 英語混在 / カタカナ多め / typo あり |
| 文体 | フォーマル / カジュアル / 質問形 / 独白 |
| 動詞 | 「書く」「作る」「迷ってる」「教えて」「設計する」「悩む」 |
| キーワード明示性 | スキル中核キーワード明示 / 暗黙（同義語） / 不在 |
| 具体度 | プロジェクト名・実 API 名あり / 一般論 / 抽象的 |
| 文の長さ | 短文（1-2 行） / 中（3-5 行） / 長（6 行以上） |
| 期待動作 | should_trigger / should_not_trigger |

## 5. プロパティテスト

| 要因 | 典型的な水準 |
| --- | --- |
| input shape | 空 / 単一要素 / 多数 / ネスト |
| input size | 1 / 100 / 10000 / メモリ限界 |
| 制約条件 | 制約満たす / 制約違反 / 境界 |
| 不変条件 | 等価律 / 単調性 / 結合律 / 冪等性 |

## 6. 契約テスト（外部 API ラッパー等）

| 要因 | 典型的な水準 |
| --- | --- |
| Request 側 | 認証ヘッダ / URL base / path / query / body / メソッド |
| Response 側 | 200 マッピング / 欠落要素の除外 / 警告 |
| Error 変換 | 4xx / 401・403 / 404 / 429 / 5xx / network / 非 JSON |
| 副作用 | API キー漏れ / requestId 伝搬 / ログ出力 |
| 入力境界 | undefined / 空文字 / null / 0 / 巨大値 |

## 7. A/B テスト・実験

| 要因 | 典型的な水準 |
| --- | --- |
| ユーザーセグメント | 新規 / 既存 / heavy / light |
| デバイス | mobile / desktop / tablet |
| 時間帯 | peak / off-peak |
| 曜日 | 平日 / 土日 |

## 要因列挙時のヒント

- **「変えたら結果が変わりうる」を要因とする**。「変わらなさそう」なものは要因にしない（過剰になる）
- **要因が 7 個を超えたら絞る**（5 要因 × 3 水準 = 243 通り、7 要因 × 3 水準 = 2187 通り）
- **期待動作も 1 要因**として扱う（pass/fail, trigger/no-trigger）。これにより負例の不足にも気付きやすい
- **要因間の交互作用が支配的**な領域（LLM eval 等）では、要因マトリクスを「カバレッジ可視化」のためだけに使い、組み合わせを機械的に網羅しない
