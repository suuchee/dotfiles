# LLM trigger eval 特有の要因設計

skill description が発火するか / しないかを評価する eval set を作る場合の、独自の要因設計と注意点。

## なぜ trigger eval が特殊か

通常のテストは「入力 → 期待出力」の deterministic な検証だが、LLM の trigger 判定は：

- **確率的**: 同じ入力でも複数回叩くと結果がブレる（同じ description でも 3 回中 2 回 trigger 等）
- **要因の交互作用が支配的**: 「日本語 + ラッパー明示 + 短文」のような特定の組み合わせで急に効きが変わる
- **「リアルさ」が効く**: 直交表で機械的に作った人工的な query は、実ユーザー発話とパターンが違って眼前のテストにならない
- **負例（trigger すべきでない）の設計が難しい**: 完全に無関係な query は trivial、近接ドメインだと判定が割れる

そのため、**通常のテスト設計で使う直交表をそのまま当てはめるのは過剰**。要因マトリクスは「カバレッジ可視化」のために使い、ケースは可能な限り**実ユーザーが実際に書きそうな文章**にする。

## LLM trigger eval の主要要因

| 要因 | 水準例 | 影響 |
| --- | --- | --- |
| **ドメイン** | 主対象 / 隣接（trigger 不要） / 完全無関係 | 主効果（最大） |
| **キーワード明示性** | スキル中核キーワード明示 / 同義語 / 暗黙 | 主効果（大） |
| **言語** | 日本語のみ / 英語混在 / カタカナ多め | 中規模 |
| **文体・口調** | フォーマル / カジュアル / 質問形 / 独白 | 中規模 |
| **動詞** | 「書く」「作る」「迷ってる」「教えて」「設計する」 | 中規模 |
| **具体度** | プロジェクト名・実 API 名あり / 一般論 / 抽象 | 中規模 |
| **文の長さ** | 短文 / 中 / 長 | 小〜中 |
| **typo / 略語 / 口語性** | きれい / typo あり / 略語多用 | 小〜中 |
| **背景情報** | 状況描写あり / 質問だけ | 小〜中 |
| **期待動作** | should_trigger / should_not_trigger | （これ自体が要因） |

## 設計手順

### Step 1: 主要因を 4-6 個に絞る

trigger 判定に最も効くのは「ドメイン」「キーワード明示性」「言語」「期待動作」の 4 つ。それ以外は 1-2 個追加する程度でよい。

### Step 2: 水準ごとのケース数を均等にする

**should_trigger と should_not_trigger は概ね 1:1**（合計 20 ケースなら 10:10）。これは skill description の precision / recall を両側評価するため。

各水準も均等を意識：
- 「ドメイン × 主対象」が 8 件、「ドメイン × 隣接」が 2 件だと、隣接の判定精度が見えない

### Step 3: 「リアルさ」を優先

要因の組み合わせを満たすために不自然な query を作るくらいなら、要因のバランスを少し崩してもリアルな query にする。

**良い query の例:**
> "Stripe の subscription 関係を扱う社内ラッパー書きたい。stripe SDK 使う前提で、社内の Vault 経由で apiKey 取得して、社内ロガーに request を流す薄い層を被せたい。何から始めるべき？"

要因マッピング:
- ドメイン: 主対象（API ラッパー設計）
- キーワード明示性: 「ラッパー」明示
- 言語: 日本語＋英語混在
- 動詞: 「書きたい」
- 具体度: 高（Stripe / Vault / ロガー / SDK）
- 文の長さ: 中
- 期待動作: should_trigger

**悪い query の例（要因のために作った人工的な query）:**
> "API クライアント作ります。日本語短文。要因 A:1 B:2"

これは直交表の要因充足のために作られていて、実ユーザー発話ではない。

### Step 4: 隣接ドメインの負例を慎重に作る

trivial な負例（「天気はどう？」等）は valuable でない。**近接ドメイン**で「trigger すべきでないが、表面的にはキーワードが似ている」を狙う：

| skill が外部 API ラッパー設計の場合 | 負例の良い例 |
| --- | --- |
| Webhook receiver の signature 検証（受け側、ラッパーではない） | ✓ |
| express の認証 middleware（サーバー側） | ✓ |
| GraphQL client の選定（HTTP REST と異なる領域） | ✓ |
| MCP server 実装（HTTP wrapper でない） | ✓ |
| 「天気は？」 | ✗ trivial すぎ |

### Step 5: 要因マトリクスでカバレッジ確認

出来上がった eval を要因マトリクスに mapping し、空セルや偏りを発見する。完璧な直交化は不要だが、極端な偏りは補正する。

| ケース | ドメイン | キーワード | 言語 | 動詞 | 期待動作 |
| --- | --- | --- | --- | --- | --- |
| #1 | 主対象 | 明示 | 日本語 | 書く | trigger |
| #2 | 主対象 | 明示 | 日本語 | 迷ってる | trigger |
| #3 | 主対象 | 明示 | 英語混在 | 書く | trigger |
| ... | ... | ... | ... | ... | ... |

水準ごとの登場回数をカウント。極端に少ない水準は補強する。

## 確率性への対処

LLM の trigger 判定は確率的なので、各 query を **3 回叩いて trigger rate を測る**のが基本（skill-creator の `run_loop.py` がそうしている）。trigger rate 67%（3 回中 2 回）以上を pass、33% 以下を fail、と扱う。

そのため eval セットのサイズは「trigger rate ばらつきの統計的有意性」を考えると 15-25 ケースが適度。100 ケースは過剰、5 ケースは少なすぎ。

## 失敗時の分析

trigger eval が失敗したケースを要因マトリクスに mapping し直す。例えば：

- 「日本語 × 暗黙キーワード」のケースが軒並み trigger しない → description に「ラッパー」以外の同義語（「クライアント」「fetch wrapper」）を追加
- 「英語混在」だけ trigger しない → description に英語キーワードを増やす
- 「短文」だけ trigger しない → description が長すぎて短文クエリで重みが薄れている可能性

このように要因単位で原因切り分けをするのが、要因マトリクスの最大の効用。

## skill-creator との統合

`~/.claude/plugins/cache/claude-plugins-official/skill-creator/.../scripts/run_loop.py` は trigger eval セット（JSON）を取って自動最適化する。eval セットを要因マトリクスベースで作っておくと、optimization の各 iteration でどの要因の水準で改善 / 悪化したかが分析しやすい。
