# Git Workflow

Git操作における規約とワークフローを定義する。

## 概要

このスキルは以下の場面で使用する：
- コミットの作成
- リポジトリの初期化
- ブランチの作成・管理
- ステージングとコミット設計
- amend操作

## Git 初期化

新しいリポジトリを初期化する場合：

```sh
git init
git branch -m main
git commit --allow-empty -m "first commit"
```

## ステージング

無関係の変更がコミットに入り込まないよう、必ずそのタスク内での変更ファイルのみを対象としてステージングする。

**推奨**: `git add -A` や `git add .` ではなく、ファイルを個別に指定する。

## コミット前の確認

コミット前に必ず以下を確認する：

1. **現在のブランチを確認** - 適切なブランチにいるか
   - main/master/develop ブランチや、変更内容と異なるブランチの場合は、新規ブランチ作成または適切なブランチへの移動を提案
2. **変更範囲の確認** - タスクに関連する変更のみか
3. **コミット粒度の確認** - revert可能な段階的設計か
4. **不要ファイルの有無** - 意図しないファイルが含まれていないか

## ブランチ設計

**基本原則: 1ブランチ = 1PR**。独立してレビュー・マージ・revert できる単位で作る。プロジェクト固有のブランチ戦略（Git-Flow 等）がある場合はそちらを優先する。

### イシュー起点で考える

ブランチ分割は「ファイルをどう分けるか」ではなく、**「何を解決するか（イシュー）」** を起点に考える。イシューの規模に応じて1つまたは複数のブランチ・PRに分かれる。規模が大きい場合、イシュー自体の分割か、段階的なPR分割を検討する。

### 分割の判断基準

以下のいずれかに該当する場合、別ブランチ・PRに分ける：

- **revert 単位が異なる**: 片方だけ戻したい可能性がある
- **レビュー観点が異なる**: レビュアーや承認フローが違う
- **変更規模が大きい**: イシューの分割を検討する
- **リリースタイミングが異なる**: 片方だけ先にマージしたい

逆に、以下の場合は同一ブランチ内でコミット分割すれば十分：

- 変更が小さく、同じ文脈で一緒にレビューできる
- 片方だけ revert する可能性が低い
- 同時にマージされることが前提

判断フローの詳細は `references/branch-design.md` を参照。

### 分岐元の選択

複数ブランチに分ける場合、それぞれの分岐元を意識する。共通の前提コミットがある場合はそこから、独立した変更であれば main/develop から生やす。

## コミット設計

一貫性のある履歴を残すため、**revert 可能な段階的コミット設計** を行う。

コミット設計時にユーザーと確認する項目：
- 変更範囲
- コミット粒度
- 不要ファイルの有無

未コミットの変更はそのままにしておき、コミット時はそのタスク内で変更したファイルのみをコミットする。

### 1ファイル内の論理的分割

1つのファイルに複数の独立した変更がある場合（例: 設定ファイルに複数機能の追加）、`git add -p` で部分ステージングし、コミットを分ける。

revert 単位が異なる変更を1コミットにまとめると、一方だけ戻したいときに困る。ファイル数ではなく変更の目的でコミットを分割する。

## コミットメッセージ

コミットメッセージは `references/commit-conventions.md` の規約に従う。

主要なルール：
- 可能な限り、その変更の理由を記述する
- 日本語の場合は文章の途中に改行を入れない
- フォーマット: `<type>(<scope>): <description>`

## ファイルの移動・名前変更

Git管理下にあるファイルやディレクトリの名前の変更・移動は `git mv` コマンドを使う。

```sh
git mv old-name.txt new-name.txt
```

## amend 操作

amend は以下の条件を満たす場合のみ使用する：

1. ユーザーが明示的に amend を指示した場合
2. 同じ変更（同じ目的・スコープ）に対するコミットである（セッション内でも別の変更が混ざる場合があるため、変更の同一性で判断する）
3. リモートに push 済みでない（force push が必要になるため）

## 誤ったブランチへのコミット対処

コミットが意図しないブランチ（特に main/develop）に入ってしまった場合の対処法。

### コミット前に気づいた場合

未コミットの変更がある状態なら、新しいブランチを作ってそちらに移動するだけでよい。変更はそのまま引き継がれる。

```sh
git checkout -b <new-branch>
```

### コミット後に気づいた場合（未 push）

CLAUDE.md の `rules/git-tips.md` にある「ベースブランチから作業ブランチへの移行」パターンを使う。ブランチ名を付け替え、元のブランチをリモートから再作成する。

### コミット後に気づいた場合（push 済み）

revert コミットで取り消し、正しいブランチに cherry-pick する。force push は避ける。
