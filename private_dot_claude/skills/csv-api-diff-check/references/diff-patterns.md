# 差分パターン分類ガイド

`clean_and_diff.py` の集計と `probe_template.py` のサンプルを見て、差分を 3 種類に分類するための判別フロー。

## 判別フロー

```
集計結果を見る
  │
  ├─ intersect = 0  →  キー指定ミス疑い (Type X)
  │                   別キー試行 or ユーザー確認
  │
  ├─ rows_with_any_diff ≈ merged_rows
  │   かつ 特定列の差件数 == merged_rows  →  全件差 (Type A)
  │                                        → 表記差を疑う → サンプル取って確認
  │
  ├─ 同じ N 行で 3 列以上が同時に空        →  欠損疑い (Type B)
  │                                        → 共通特徴を探す
  │
  └─ 差件数が散発 (1〜数件)               →  実値差 (Type C)
                                            → 件数だけ報告
```

## Type A: 表記差（フォーマット差・ロケール差）

### 兆候
- 特定列だけ全行差分（diff_count == merged_rows）
- サンプルを見ると「値の意味は同じだが表記が違う」

### 典型例

| カテゴリ | api 側 | csv 側 | 切り分け |
| --- | --- | --- | --- |
| 日付セパレータ | `2026-08-28` | `2026/08/28` | 区切り文字差 |
| 日時 → 日付丸め | `2026-03-22T11:42:38+09:00` | `2026/03/22` | 時刻成分の有無、TZ 解釈 |
| 和暦 | `2026-05-01` | `2026年05月01日` | 表記体系差 |
| 時刻ゼロ埋め | `9:00` | `09:00` | 桁数差 |
| enum vs ラベル | `done` | `終了` | 英語 enum / 日本語ラベル |
| ラベル + 値 | `E` | `E - 0%` | 値の同梱有無 |
| 欠損値表記 | `指定なし` | （空文字） | 「指定なし」を明示するか |
| 無効ユーザー | `田中` | `田中（無効）` | サフィックス付与 |
| 空白文字 | `本文: \n佐藤` | `本文:\n佐藤` | コロン後 / 改行前のスペース |
| エンコード | `��松` | `??松` | 機種依存文字の文字化け |

### 対応案

| 案 | 場所 | 向いている時 |
| --- | --- | --- |
| 取り込み層 shim | `apps/<app>/src/shared/csv-compat/` | BI 側を変更できない / すぐ揃えたい |
| BI 側変換 | BigQuery view / Looker Studio Calculated Field | API ネイティブを保ちたい / 下流が複数 |
| 揃えない | — | BI 側がフィールドの型認識で吸収できる場合（日付型として認識される等） |

判断軸を明示してユーザーに選んでもらう：

- **責務分離**: 取り込み層は API ネイティブ保持が綺麗（Bronze/Silver/Gold パターン）
- **可逆性**: 取り込み層で寄せると元値が失われる
- **既存コスト**: BI 側に変更権限がない / 即時対応が必要なら取り込み層
- **将来移行**: shim 構造で切り分ければ後で BI 側に移植しやすい

## Type B: データ欠損（取り込み漏れ）

### 兆候
- 同じ N 行で 3 列以上が同時に api 側で空（csv 側には値あり）
- 「親 entity 関連の列」「カウント系の列」が同時に欠ける
- 特定期間 / 特定種別に偏っている

### 切り分け方

`probe_template.py` の `main_pattern` モードで以下を確認：

1. **共通する期間**: 「2026/05/01 以降」など、ある時点からのデータに偏っているか
2. **共通する分類**: アクション登録先種別・レコードタイプ等が揃っているか
3. **取れている列**: 主 entity（案件名・担当者名）は取れているか、関連 entity（取引先・グループ）が落ちているか
4. **API レスポンスの fullness**: list API と detail API でレスポンス内容が違わないか

### 典型原因

| 原因 | 対応 |
| --- | --- |
| list API が関連 entity を含まない | 該当行だけ detail API で補完（`/items/{id}` を追加コール） |
| `include=` / `expand=` パラメータ未指定 | API クライアントのオプションを調整 |
| API 仕様変更で項目が削除された | SaaS 側に問い合わせ |
| 取り込みコードの分岐漏れ | 該当 entity の extract ロジックを修正 |

### 検証パス

最短：N 件のうち 1 件について、SaaS 側の管理画面 or detail API で実際の値を確認 → list レスポンスに含まれているはずなのに落ちているのか、そもそも返ってこないのかを判別。

## Type C: 実値差（タイムラグ・状態変化）

### 兆候
- 散発的な差（merged のうち数件〜数十件）
- サンプルを見ると「値が違うが、どちらも正しい時点でのスナップショット」

### 典型例

- csv エクスポート後に SaaS 側でレコードが更新された
- フェーズ・ステータス・契約確度が遷移した
- 担当者の交代

### 切り分け方

`最終更新日` 列があれば、その差から判別できる：

```python
# 日付に丸めて比較する補助スクリプト
api_date = pd.to_datetime(api[last_updated]).dt.date
csv_date = pd.to_datetime(csv[last_updated]).dt.date
delta = (api_date - csv_date).dt.days
# delta = 0 が大半 → 555件中差は実は数件、と判明する
```

タイムスタンプの粒度差（秒まで vs 日付のみ）を吸収すると、555 件全差が実は数件、ということが頻繁にある。

### 対応

- 件数だけ報告する
- BI 側で「直近 N 日」のように期間フィルタを入れる
- 検証用 CSV を取り直してもらう

## Type X: キー指定ミス

### 兆候
- intersect = 0
- api 側のキー列で大量の重複（ユニーク値が極端に少ない）
- 列ズレや粒度違いを疑う

### 対処
- ユーザーに「キー列の中身を 1 行だけ見せてよいか」を確認
- それでも特定できなければ、ID 列の上位サンプルを出して列ズレを確認
- 別キー候補（ID+日付など）を試す

## まとめ報告のテンプレート

```
| ペア | 検算結果 | 残る注目点 |
| --- | --- | --- |
| <pair> | ✅ | 値差 N 件（タイムラグ） |
| <pair> | ⚠ 表記差 | <列名>: <パターン> → 取り込み層 / BI 側 / 不要 |
| <pair> | ⚠ 欠損 | <共通特徴>: <仮説>、要追加調査 |
| <pair> | ❌ キー不一致 | <理由>、ユーザー確認待ち |
```
