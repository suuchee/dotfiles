# csv-api-diff-check

公式 API 経由で取得したデータ（A 側）と、CSV エクスポート（B 側）を突き合わせ、**実値差なのか・表記差なのか・データ欠損なのか**を切り分けるためのスキル。BI 移行・データ移管・検算タスクで頻繁に使う。

このスキルは「**人間に見せる前に、機械で集計してから、必要な部分だけ中身を出す**」という段取りに沿って動く。プライバシー保護とコンテキスト節約の両方の意味で重要。

## いつ使うか

次のような依頼に対して必ず使う：

- 「CSV と API の整合性を確認したい」「数値突合してほしい」「検算したい」
- 「BI 元データと公式 CSV エクスポートを突き合わせたい」
- 「API 取り込み後のシートと管理画面 CSV の差を取りたい」
- 「マツリカ / freee / Stripe 等の SaaS で API と CSV の表記が違わないか確認」
- 「同じデータの別経路同士で差分を出して、表記差か実値差か判別したい」

## 原則

### 1. 中身を可能な限り見ない

- ヘッダ・行数・空列・差分件数といった**集計値**だけで判断できる段階では、それで止める
- 上位 N 件のサンプルを出すのは「差分の性質を判別する」局面に限定する
- サンプルを出すときも、長い文字列は **80 字程度に短縮**して出す
- 個人情報・顧客名等が含まれる可能性があることを意識する

### 2. ユーザー確認を最初にまとめる

実装に入る前に、最低限以下を確認する：

1. **ペア対応**: どの A 側ファイルとどの B 側ファイルが対応するか
2. **空列判定の基準**: 「全行が空文字または欠損」を空列とみなして良いか
3. **マージキー**: ID 列 / ID+日付など、行を一意に特定するキー
4. **同名なし列の扱い**: A 側で空・B 側に同名列なしのケース、B 側独自の空列のケースをそれぞれどう扱うか

ペアが揃わない・対応関係が曖昧なまま実装に入ると、infrastructure-level の差（粒度違い・期間違い）が値差として現れて判断を狂わせる。

### 3. 集計 → サンプル → 深掘り の段階を守る

最初から全件・全列の中身を出さない。

1. **集計**: 行数・空列・キー集合・差分件数 を `report.json` にまとめる
2. **サンプル**: 差分件数が大きい列について上位 5 件だけ確認
3. **深掘り**: 特定パターン（N 件で複数列同時に空など）が見つかったら、該当行を絞って詳細確認

## ワークフロー

### Step 1: ファイル配置と作業ディレクトリ準備

```
<base>/
├── api/   # A 側: API 取得データ（CSV 化したダンプ）
├── csv/   # B 側: CSV エクスポート
└── _work/ # 作業用（スクリプト・出力先）
```

`_work/` を作って、その中でスクリプトを実行する。

### Step 2: ヘッダと空列を抽出（中身を見ない）

バンドルスクリプト `scripts/inspect_headers.py` をコピー or 直接実行。

```bash
uv run inspect_headers.py --api-dir ../api --csv-dir ../csv
```

出力（JSON）には各ファイルの行数・列名・空列・日付候補列が含まれる。**この段階で中身は一切出さない**。

結果から：
- 列名から「ペア対応の妥当性」を確認
- 空列の有無で「データ取込の欠落」の見込みを立てる
- 日付候補列（`日`・`time`・`date` を含む列名）でマージキー候補を仮置き

### Step 3: ユーザーへペア対応 / 削除ルール / マージキーを確認

`AskUserQuestion` で次を確認する。回答が選択肢化できる場合は必ず AskUserQuestion を使い、地の文の箇条書きで選ばせない。

1. **ペア対応**: ヘッダから推測したペア対応で合っているか
2. **空列削除ルール**:
   - A 側で空・B 側に同名列あり → 両方削除
   - A 側で空・B 側に同名なし → A 側だけ削除（比較対象外）
   - B 側独自の空列 → B 側削除 + A 側に同名あれば A 側も削除
3. **マージキー**: ID 単体 / ID+日付 / 複合キー
4. **比較粒度**: キーマージ / 日付集計 / 列存在チェックのみ

### Step 4: クリーンアップ + 集計（中身を見ない）

バンドルスクリプト `scripts/clean_and_diff.py` をコピーし、確定したペア対応とマージキーを `PAIRS` 配列に反映して実行する。

```bash
uv run clean_and_diff.py
```

出力：
- `_work/cleaned/<pair>__{api,csv}.csv` — 空列削除後 CSV
- `_work/report.json` — 集計結果
- 標準出力にコンパクトサマリ

コンパクトサマリは「ペアごとの行数・削除列・キー集合・列ごと差分件数・日付差分」が並ぶ。ここまでで「**全列差・特定列だけ差・差なし・キー不一致**」のどのパターンか判別できる。

### Step 5: 結果の解釈

`report.json` を読み、各ペアを次のいずれかに分類する：

| パターン | 兆候 | 解釈 |
| --- | --- | --- |
| ✅ 健全 | intersect ≈ csv 行数 / 値差ごく少数 | 実値差として確定。件数だけ報告 |
| ⚠ 全件差 | merged 全件に差 / 特定列の差件数 == merged 行数 | **表記差（フォーマット差・ロケール差）疑い** → Step 6 へ |
| ⚠ N 件で複数列同時に空 | 同じ N 件で 3 列以上が同時に空 | **データ欠損疑い**（関連 entity 取り込み漏れ） → Step 7 へ |
| ❌ intersect=0 | キーが交差しない | **キー指定ミス**（列ズレ・粒度違い）疑い → ユーザーに確認 |

### Step 6: 表記差の切り分け（サンプル抽出）

`scripts/probe_template.py` をベースに、対象ペア・対象列・キー列を埋めて実行する。上位 5 件だけ出力し、長い文字列は 80 字に切る。

典型パターン（references/diff-patterns.md に詳細）：

- **日時のゼロ埋め差**: `9:00` vs `09:00`
- **日付フォーマット差**: `2026-08-28` vs `2026/08/28` / `2026年08月28日`
- **日時 vs 日付丸め**: `2026-03-22T11:42:38+09:00` vs `2026/03/22`
- **enum vs ラベル**: `done` vs `終了`
- **ラベル + 値の同梱**: `E` vs `E - 0%`
- **空白文字差**: 改行直前の半角スペース有無、コロン後のスペース有無
- **欠損値表記差**: `指定なし` vs 空文字 / `null` vs 空文字
- **無効ユーザー表記**: `田中さん` vs `田中さん（無効）`
- **エンコード差**: 機種依存文字の文字化け

### Step 7: データ欠損の深掘り

「N 件で複数列同時に空」が出たら、その N 件の共通特徴を探す。`scripts/probe_template.py` を改造し、共通する列の値を並べて表示する：

- 期間（作成日範囲）
- アクション登録先種別 / レコードタイプなどの分類列
- 案件名・担当者は埋まっているか（取得は出来ている）
- どの関連 entity が落ちているか（取引先・グループ・カウント系）

特徴が「特定期間以降」「特定種別」のような形で揃ったら、API の list レスポンスの fullness（一覧 vs 詳細）変化や、取り込みロジックの分岐漏れを疑う。

### Step 8: 対応案の提示

最後にユーザーへ次のように整理して提示する：

- **表記差**: 取り込み層 shim で揃える / BI 側（Looker Studio / BigQuery view）で揃える / 揃えない を**判断軸つきで提示**し、ユーザーに選んでもらう
- **実値差**: タイムラグや状態変化として許容する
- **データ欠損**: 取り込みロジックのバグ調査として別タスクに切り出す（detail API 補完、include パラメータ、SaaS 側問い合わせ）

判断軸の例：
- 「BI を変えずに済むか」 vs 「データ正規性を保つか」
- 「将来 BigQuery 化したときに丸ごと外せるか」（shim を独立配置するメリット）
- 「下流が増えたときに表記を押し付けないか」

### 表記差 shim の実装提案パターン

ユーザーが「取り込み層で揃える」を選んだ場合に推奨する構造：

```
apps/<app>/src/shared/csv-compat/
  date.ts        # 日付・日時の表記揃え（pure functions）
  mapping.ts     # enum → ラベル変換
  index.ts       # re-export
```

- 副作用なしの純粋関数だけにする（テスト容易性）
- `csv-compat/` というディレクトリ名で「BI 互換のための寄せ処理」と一目で分かる
- 将来 BI 側で吸収できるようになったら、shim ディレクトリごと削除して extract を素のフィールド参照に戻すだけ
- shim ファイルの冒頭コメントに「BI 互換のための暫定処置・将来削除予定」と明記

## バンドルファイル

- `scripts/inspect_headers.py` — Step 2 のヘッダ + 空列抽出
- `scripts/clean_and_diff.py` — Step 4 のクリーンアップ + 集計
- `scripts/probe_template.py` — Step 6 / 7 のサンプル抽出テンプレート
- `references/diff-patterns.md` — 表記差・実値差・データ欠損の判別フロー詳細
- `evals/evals.json` — テストケース（ドラフト）

## 出力の最終まとめテンプレート

調査が終わったら、ユーザーに次の形でまとめを提示する：

```
## 集計結果サマリ

### <ペア名>
- 行数: A=N1 / B=N2
- 削除列: A 起点 X 列 / B 独自 Y 列
- intersect: M 件
- 値差: merged のうち K 行
  - <列名>: 件数 / 切り分け（表記差 / 実値差 / 欠損疑い）

### 全体まとめ
| ペア | 検算結果 | 残る注目点 |
| --- | --- | --- |
| ... | ✅ / ⚠ / ❌ | <内容> |

## 対応案
1. 表記差: ...
2. 実値差: ...
3. データ欠損: ...
```
